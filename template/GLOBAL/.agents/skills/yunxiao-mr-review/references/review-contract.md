# 云效 MR 审查契约

## 最小输入

优先接受完整 MR 链接；也可以使用项目规则明确的逻辑 Profile、组织、仓库 ID/全路径和 MR 编号。必须交叉核对项目资源路由与本地 `git remote -v`，不能仅凭目录名匹配。

## 证据清单

- MR ID、URL、标题、描述和作者；
- 最新源分支 SHA、目标分支 SHA 和提交列表；
- 变更文件、完整 diff 与二进制/大文件；
- unresolved discussions、评审人数和具体状态；
- mergeability、冲突、草稿状态；
- 流水线/检查名称、运行 ID、结论和日志入口；
- 本地测试命令、结果和未覆盖边界。

## 发现格式

每条发现包含：严重度、简短标题、证据位置、问题机制、用户可见影响、建议修复。仅当代码行为、测试或明确契约支持时才下结论。

没有高可信发现时，输出“未发现阻断性代码问题”，并单列仍未验证的系统集成、生产环境、数据迁移、安全或性能边界。

## 自动评审闭环

用户明确要求使用本 Skill 或项目覆盖层审查 MR 时，授权范围仅自动包含：

- 对高可信问题发布精确行内评论；
- 解决经最新 patchset 与讨论证据确认已经修复、失效，或被用户明确接受/暂缓的现有评论；
- 证据完整、风险相称验证通过且没有问题时提交“通过”评审。

行内评论必须锚定当前 patchset 的真实致因行，逐项发布，并包含严重度、机制、触发条件、影响和修复建议。写入前锁定最新 SHA 和 patchset，写入后按评论 ID 回读；快照变化时停止并重新审查。

逐条复核未解决评论在最新 patchset 上的现状：仍有效或无法验证的评论保持未解决并阻断通过；已经修复、因代码演进而失效，或被用户明确接受/暂缓的评论直接解决并回读。不得仅因评论锚定旧 patchset 就自动认定已失效，也不得让已经闭环的历史评论长期阻断评审。

首次审查必须一次性覆盖当前完整 MR，并记录目标 SHA、源 SHA/patchset、文件范围和验证结果作为审查基线。复审必须先回读该基线，只审查原评论修复、基线之后的新增差异，以及验证这些变化所需的直接影响链；不得把未变化且已经审过的旧代码重新当成普通审查对象。复审新增发现必须标明“修复引入”或“新增代码引入”。只有严重安全漏洞、数据损坏或不可逆业务错误等必须立即阻断的首审遗漏，才允许例外追加，并应透明说明遗漏与阻断理由。

存在任何仍有效或无法验证的高可信问题、未解决讨论、冲突、必需检查失败或影响结论的证据缺口时不得通过。若当前版本只有既有评论修复、没有其他新增差异，且适用评论全部解决、其余门禁通过，应自动解决评论并立即提交“通过”评审，不要求用户再次确认，也不得再开启一轮全量审查。请求修改、关闭、合并、删除源分支、重跑检查和部署仍分别确认，不得从审查、评论、解决评论或通过评审中推导。所有写入都必须回读实际状态。
