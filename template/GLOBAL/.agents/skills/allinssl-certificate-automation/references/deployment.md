# DNS、入口部署与失败保障

## DNS 与账号

核验真实调用主体和域名管理接口，DNSPod 解析域名与注册域名列表不一定相同；不能因注册接口无结果判断用户没有域名。对每个 zone 验证域名读、TXT 创建/删除权限，并采用最小权限策略；子账号或凭据创建仍须用户授权。

云主机所属账号可能不同于 DNS 账号；不能从 DNS 授权推导 CVM/安全组权限。读取现有 A/AAAA/CNAME、暂停状态与用途，防止更新后 CNAME 冲突或旧 AAAA 导向其他入口。变更前记录旧值与 TTL；解析验证使用可信解析器及外部观察，识别本机代理 Fake-IP，不把代理地址当作公网 DNS。

自动 ACME TXT 创建与清理只操作本次验证记录，不删除其他 TXT。通配符证书使用 DNS-01；监控应列出实际业务主机名，不能监控 *.example.test。

## SSH 认证

每台服务器独立密钥、独立授权 ID，按稳定 Profile 命名；例如“服务器 - Linux - <profile>”。凭据不按应用复用。现有 root 授权改密钥不等于已建立最小权限部署用户，两者分别记录。

先严格核验指纹与公私钥匹配，再追加公钥，保持所有旧授权；从 ALLinSSL 实际执行环境验证登录后才修改存储配置。转换时清空存储密码，但不轮换服务器密码或关闭密码登录，除非用户另行明确授权。API 原生连接测试与实际 SSH 登录均验证；临时副本随后清理。

新部署优先非 root 用户；只赋予证书目录写权限及准确的配置检测/重载命令。目录所有权不可扩大到其他站点，sudo 不允许任意 shell 或全量 systemctl。证书私钥通常 0600；父目录允许实际 TLS 服务按运行主体读取。

## TLS 入口前置条件与事务

1. 确认真正的 TLS 终止点。Nginx、Caddy、云负载均衡、CDN 等不同部署目标各自有上传、验证与生效机制；服务器授权本身不能替代入口准备。
2. Nginx 检查安装、版本、服务状态、站点、监听端口、后端及现有共享服务影响。需要安装时先完成依赖，再安装站点文件，避免 sites-available 尚不存在。缺少安装/网络权限则报告缺项。
3. 配置域名、证书和 key 路径；HTTP 跳转、WebSocket、长连接、上传限制按应用要求选择。仅打开需要的公网端口，后端可保持回环监听。示例语法须核对 Nginx 版本。
4. 新入口不得将未设管理员的应用无保护公开暴露；先完成管理员初始化或使用访问限制，在允许范围内逐步放开。
5. 证书与私钥匹配、SAN、链、有效期先检查；使用同文件系统暂存、受限回退副本与原子替换。回退材料包括当前证书/私钥，必须留在服务器受限位置，不进入 Git。
6. 写入之后先配置检查（Nginx 为 nginx -t），成功后平滑 reload；不能用 restart 替代或把最后一条 chmod 成功当作部署成功。所有命令失败必须传播非零状态。
7. 重新读取公网服务实际呈现证书，比较指纹/SAN/有效期与新证书，检验多个目标都加载。失败则恢复旧文件和配置，检查后重载并回读。
8. 历史 skip=1 会跳过曾成功部署的同指纹证书；若服务器回退、迁移或实际证书已漂移，应核实并在授权范围纠正跳过条件，不能只重新运行工作流。

## 失败双渠道保障

区分申请失败、DNS 授权失败、每个部署失败、配置检测/reload 失败、通知自身失败及调度器停止。

仅在 deploy 后放一个结果分支可能遗漏 apply 失败：按对应版本引擎核验失败后是否继续 childNode、execute_result_branch 的 fromNodeId 指向以及 StatusFailed 状态。为 apply 与每个部署目标建立实际可达的失败处理，或使用版本支持的工作流整体失败机制；无法表达时必须报告缺口。增加外部整体历史/调度监测是另外一项需要用户授权的系统工作，不擅自创建 Codex 心跳或 cron。

两个通知要独立尝试；顺序 notify 链若第一个返回错误后终止，不满足双来源保障。使用已验证的并行/独立失败分支、引擎支持的继续执行机制，或经授权的外部调度兜底。不得把 notify 的 skip 选项误当作“错误后继续”。

通知只包含项目/域名、失败阶段、时间和可处理摘要，不含密钥、原始日志或个人资料。同两个来源也用于每域名监控，但正常证书监控无法替代整体工作流失败检测或证明调度器存活。

测试失败路径优先隔离环境和无副作用的测试替身，不使生产证书无效、不改真实 DNS 造失败、不重复调用 CA。外部消息测试经授权后分别确认接收；通知失败报告独立状态，保留成功渠道，避免告警风暴。
